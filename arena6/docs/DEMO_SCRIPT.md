# Demo Script (about 10 minutes)

Audience and length were not specified, so this assumes SIH judges and 10 minutes. Shorten by dropping Part 5; lengthen with Part 6 questions.
The engines below come from the seeded data (seed 42, `demo_scenarios.json`). If you change the seed or volumes, re-read `arena6/sample_data/demo_scenarios.json` and swap the numbers.

| Role | Engine (`unit_nr`) | Aircraft | Story |
| :--- | :---: | :--- | :--- |
| Critical | **73** | VT-BXO, Hyderabad | Lowest RUL in the fleet (12 cycles). P1 work order `WO-2026-0020` is `PLANNED` with no repair slot yet |
| AOG | **76** | VT-RCS, Delhi | RUL 40. P1 work order `WO-2026-0007` is `WAITING_PARTS`: Core Speed Sensor (Nc) `SP-0189` is out of stock, lead time 41 days |
| Warning | **16** | VT-SGW, Hyderabad | RUL 65, early drift, no work order yet |
| Healthy | **64** | VT-XIH, Mumbai | RUL 276, nothing to do |

## Before you start (15 minutes earlier)

```powershell
python -m arena6.seed_db                       # fresh demo data + telemetry for units 3,16,19,26,56,60,64,73,76,100
uvicorn backend.main:app --port 8000           # terminal 1
streamlit run dashboard/app.py                 # terminal 2
python -m arena6.show_demo_data                # terminal 3 - keep the output on screen
```

Open in tabs: `http://127.0.0.1:8000/docs`, `http://localhost:8501`. Check `http://127.0.0.1:8000/health` shows all models loaded.
Run through the whole script once; take the screenshots in `arena6/screenshots/README.md` while you do.

## Part 1 - The problem (0:00-1:00)

**Say:** "An unplanned engine failure grounds an aircraft and costs the airline heavily for every day it stays on the ground. We predict how many flight cycles each engine has left, say why, and connect that to the maintenance plan."
**Show:** nothing yet, or the architecture diagram in `docs/ARCHITECTURE.md`.

## Part 2 - The fleet in one screen (1:00-2:30)

**Show:** terminal 3, the first two tables.
**Say:** "50 aircraft, 100 engines from NASA C-MAPSS. 26 engines are critical, 21 warning, 53 healthy. The critical list is sorted by remaining life; the lowest is engine 73 with 12 cycles left, on VT-BXO in Hyderabad."

## Part 3 - One engine, end to end (2:30-6:00)

1. **Dashboard** (`localhost:8501`): select **Unit 73**, tab *Degradation & Telemetry*. "Sensors drift as the engine wears." Switch the model radio between TCN, LSTM and XGBoost.
2. **Swagger** `POST /api/v1/predict/rul` with `{"unit_nr": 73, "model_type": "tcn"}`. "This reads the last 30 stored cycles from the database and returns RUL, health index and status." Expect a low RUL (true value is 12); **try it in rehearsal and note the actual number**.
3. Tab *Anomaly Radar & Lead Time*: "Isolation Forest flags abnormal behaviour before failure."
4. Tab *AI Explainability (SHAP)* or Swagger `GET /api/v1/explain/73`: "Not a black box: these sensors drive the low RUL."

> Honest note for Q&A: the dashboard's KPI "Predicted RUL" is currently simulated around the true value (BUG-009). The numbers from Swagger are the real model output. Present the API call as the proof of the model and the dashboard as the cockpit layout, unless Arena 5 has connected it to the API by demo day.

## Part 4 - From prediction to action (6:00-8:00)

**Show:** terminal 3, tables *Open work orders* and *Next free repair slots*.
**Say:** "The alert became defect log `DEF-0038` and P1 work order WO-2026-0020: overhaul of engine 73. It has no slot yet. Hyderabad's next free slot is 11 November, nine days away (slots are counted from the seed's start date), while the engine has 12 flights left. This is the gap predictive maintenance closes: we know early enough to rearrange the schedule."

## Part 5 - When the part is missing (8:00-9:00)

**Show:** table *Aircraft on ground (AOG)*.
**Say:** "VT-RCS is grounded in practice: its P1 job is blocked because a Core Speed Sensor is out of stock in Delhi with a 41-day lead time. A prediction is only useful if parts and hangar time are ready, so the system tracks both."

## Part 6 - Why trust it (9:00-10:00)

**Show:** dashboard tab *Model Leaderboard* (numbers from `models/artifacts/benchmark_metrics.json`).
**Say:** "We compared three models on 100 test engines. The TCN is best with RMSE 10.6 cycles; XGBoost 11.4, LSTM 10.9. Our scoring penalises late predictions harder than early ones, because an optimistic prediction is the dangerous kind. Anomaly detection: 4% false alerts, 0% missed failures."

## Likely questions

| Question | Answer |
| :--- | :--- |
| Is the maintenance data real? | No - synthetic, generated by us and linked to the real NASA C-MAPSS engines. The real part is the sensor data and RUL |
| Why 12 cycles = urgent? | A cycle is one flight. An aircraft flying several times a day uses 12 cycles within days |
| Does it use Kafka? | Streaming is simulated inside the API; Kafka settings and containers exist, but there is no Kafka client code yet (BUG-012). Say "Kafka-ready", not "uses Kafka" |
| How is detection lead time 237 cycles possible? | Be ready to explain the definition (BUG-015) or avoid quoting that number |
| What if the network or model fails? | API returns clear errors (503 when models are not loaded) - see `tests/test_api_errors_missing_data.py` |
| How did you test it? | 160 automated tests: data integrity, database seeding, valid / invalid / missing-data API calls |
